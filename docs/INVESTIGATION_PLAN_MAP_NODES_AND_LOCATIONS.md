# Investigation Plan (IP): Map nodes, location data integrity, and related issues

**Date:** 2026-04-21  
**Purpose:** Answer whether places are “real” vs vaporware, explain why map markers may not appear, document architecture and failure modes, and list outstanding product items for review **before** further code changes.

---

## 1. Executive summary

| Question | Answer |
|----------|--------|
| Are locations hallucinations / vaporware? | **No.** They are **seeded rows** in PostgreSQL from migration `011_replace_places_from_research.sql`, with explicit `ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography` coordinates. The app does **not** invent places at runtime from an LLM. |
| Why might nodes not show? | Most likely **frontend Mapbox + React lifecycle** (style reload / effect dependencies), secondarily **empty or malformed `coordinates`** in API responses, or **missing env** (`VITE_MAPBOX_TOKEN`). |
| Is data “missing” in general? | If production DB never ran migration 011 (or coordinates were cleared), the feed would be empty—that is an **ops/DB** issue, not a model hallucination. |

## 2. Evidence: locations are real database rows

### 2.1 Source of truth

- **Table:** `public.places`
- **Geometry:** `coordinates` column is **PostGIS `geography(Point)`**, populated with real lng/lat pairs in SQL (example from `011_replace_places_from_research.sql`):

```sql
ST_SetSRID(ST_MakePoint(-73.9216, 40.9547), 4326)::geography,
```

- **Migration note:** File header states rows are generated by `scripts/build-places-from-research.mjs` and that the migration **replaces all** `places` rows (`DELETE FROM places;` then bulk `INSERT`). So the catalog is **curated seed data**, not runtime AI output.

### 2.2 Spatial API

- **RPC:** `places_nearby(lat, lng, radius_m, mode_filter)` in `005_spatial_rpc_and_moderation.sql`
- **Behavior:** `ST_DWithin` on `coordinates`, filters by `mode` / `both`, returns `SETOF places` ordered by distance, limit 50.
- **Grants:** `EXECUTE` granted to `anon` and `authenticated` so the anon key used by the web app can call it (assuming RLS on `places` allows read—see live project policies).

### 2.3 What the client requests

- **Select list:** `PLACES_LIST_SELECT` in `src/lib/placesSelect.js` explicitly includes **`coordinates`** among columns for list/map/card use.
- **Home fetch:** `src/pages/Home.jsx` merges RPC results with additional `from('places').select(PLACES_LIST_SELECT)` rows to fill the catalog up to `PLACES_LIST_CAP`.

**Conclusion:** If Supabase returns rows with valid `coordinates`, the data model supports map markers. Any “no dots” issue is almost certainly **client rendering / Mapbox**, not “fake places.”

## 3. Data path: from Supabase to yellow dots

```
Supabase (places + places_nearby RPC)
    → Home state `places` / merged list
    → `filteredPlaces` (intention, intensity, hide visited, saved only, sanctuary tradition, sort by distance)
    → `<Map places={filteredPlaces} … />`
    → `placeMarkers()` creates DOM elements and `mapboxgl.Marker` per row with `place.coordinates`
```

Markers are skipped only when:

```js
if (!place.coordinates) return
```

(from `src/components/Map.jsx`)

So **null coordinates** ⇒ no marker for that row.

## 4. Coordinate shape expected by the map

The map assumes **GeoJSON-style** nesting:

```js
place.coordinates.coordinates  // [lng, lat]
```

PostgREST typically serializes PostGIS geography to **GeoJSON** in JSON responses, which matches this shape. If an environment returned **EWKB hex**, **a string**, or **bare `[lng,lat]`** without the wrapper, `place.coordinates.coordinates` would be wrong and markers could misplace or fail (the current code also falls back to a **hard-coded Philadelphia** pair if inner coordinates are missing—dangerous for debugging because something still “shows” at the wrong spot).

**IP recommendation:** Add a **single normalization helper** (e.g. `getLngLat(place)`) that accepts GeoJSON `Point`, and optionally logs/skips invalid rows in dev—**defended** because it makes the contract explicit and avoids silent Philly fallback.

## 5. Primary architectural issue: `placeMarkers` in the mode-change effect dependency array

**Location:** `src/components/Map.jsx`

The effect that runs on **mode** change (Sanctuary ↔ Theophany) registers `style.load` and calls `map.setStyle(...)`.

**Observed pattern (problem):** That effect’s dependency array includes **`placeMarkers`**. But `placeMarkers` is a `useCallback` that depends on **`places`** (and selection/visit sets). Therefore **every time `places` updates** (initial fetch, refetch, filter changes that alter the list reference), `placeMarkers` identity changes and the effect can re-run **even when `mode` did not change**, causing **`setStyle` to run again**. A style reload **clears** the WebGL marker layer context; markers must be re-added. If timing races with `isStyleLoaded()` or duplicate `style.load` handlers, users see **intermittently zero markers**.

**Defense (why this explains “nodes not showing”):** This is a classic **stale dependency** bug: “mode styling” is conceptually only about `mode`, but it was coupled to “data identity,” so data refreshes behave like repeated mode switches.

**Recommended fix (for implementation phase):**

- Hold the latest `placeMarkers` in a **`useRef`** (`placeMarkersRef`) updated in a small `useEffect`, and have `style.load` call `placeMarkersRef.current()`.
- Make the **mode-only** effect depend on **`[mode]`** (plus stable helpers if needed), **not** on `placeMarkers`.

This matches the fix that was validated in earlier iterations of this project; it should be re-verified on the current `Map.jsx` branch (especially after the `8ad7afc` “bidirectional map” work added `ensureContainerIntegrity` / `buildMap`).

## 6. Secondary issues: style load race and container recovery

### 6.1 `isStyleLoaded()` guard

An effect that re-runs `placeMarkers` when `placeMarkers` changes used to **return early** if `!map.current.isStyleLoaded()`, with **no listener**—markers never placed until another event fired.

**Defense:** Under load, **register `once('style.load', …)`** if style is not ready, so markers always attach after transitions.

### 6.2 `buildMap` / `ensureContainerIntegrity`

The map can **destroy and recreate** the map instance when the DOM container loses Mapbox’s expected structure. `buildMap` currently lists **`placeMarkers`** in its `useCallback` dependencies, which ties map **rebuild** to **data churn**—worth auditing so refetch doesn’t cause unnecessary full rebuilds.

## 7. Environment and Mapbox

| Check | If failing |

**Defense:** Confirm production env and browser console on a device where markers fail.

## 8. “Lack of data” vs “data not shown”

| Symptom | Likely cause |
|---------|----------------|
| **0 places** in feed + map | DB empty, RLS blocking `select`, RPC error, or `hasSupabaseEnv` false locally. |
| **Places in list, 0 on map** | Filtered list empty, or **map lifecycle** (Section 5), or coordinates missing on rows. |
| **Dots wrong region** | `mapCenter` vs user location; or bad coordinate parsing (Section 4). |

**SQL checks (run in Supabase SQL editor):**

```sql
-- Count rows with coordinates
SELECT COUNT(*) FROM places WHERE coordinates IS NOT NULL;

-- Sample coordinate JSON shape (adjust limit)
SELECT id, name, city, coordinates::text FROM places LIMIT 5;
```

**Defense:** If counts are hundreds and coordinates non-null, data is present; prioritize client map logic.
